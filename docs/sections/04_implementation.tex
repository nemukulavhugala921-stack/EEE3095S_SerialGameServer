\section{Implementation}
\label{sec:impl}

% ── Mark scheme: 15 marks ─────────────────────────────────────────────────────

This section details four key implementation challenges across the embedded firmware and host client. For each challenge, we examine the concrete engineering constraint, present the verified code implementation, and discuss the failure modes of naive alternatives.

\subsection{Interrupt Ring Buffering and Flag Clearance Prevent UART Lockup}

At 115\,200 baud, bytes arrive at the microcontroller every $86.8\,\mu\text{s}$. If the CPU were busy updating LED indicators or evaluating game logic, synchronous polling would drop characters. More critically, serial bus noise or USB cable re-enumeration triggers Overrun (\texttt{ORE}), Framing (\texttt{FE}), or Noise (\texttt{NE}) flags in the STM32 USART peripheral. According to the reference manual~\cite{rm0091}, an unhandled overrun error inhibits the Receive Data Ready (\texttt{RXNE}) flag, permanently freezing UART reception.

The naive alternative—using blocking \texttt{HAL\_UART\_Receive()} in the main loop—introduced visible latency into LED updates, missed button presses, and caused the UART to lock permanently whenever the USB cable was disconnected and reconnected, requiring a full power cycle.

\begin{lstlisting}[language=C, caption={Interrupt ring buffer and hardware error clearance (\texttt{protocol.c}).}, label=lst:ringbuf]
void protocol_rx_isr(void) {
    if (g_huart == NULL) return;
    uint16_t next = (g_ring_head + 1) % PROTOCOL_RING_BUFFER_SIZE;
    if (next != g_ring_tail) {
        g_ring_buf[g_ring_head] = g_rx_isr_byte;
        g_ring_head = next;
    }
    HAL_UART_Receive_IT(g_huart, &g_rx_isr_byte, 1);
}

void protocol_error_isr(void) {
    if (g_huart == NULL) return;
    /* Clear flags to prevent hardware receiver lockup */
    __HAL_UART_CLEAR_OREFLAG(g_huart);
    __HAL_UART_CLEAR_FEFLAG(g_huart);
    __HAL_UART_CLEAR_NEFLAG(g_huart);
    HAL_UART_Receive_IT(g_huart, &g_rx_isr_byte, 1);
}
\end{lstlisting}

Listing~\ref{lst:ringbuf} shows our interrupt and error-recovery handlers in \texttt{protocol.c}. Incoming bytes are enqueued into a circular ring buffer sized at \texttt{PROTOCOL\_RING\_BUFFER\_SIZE} (128 bytes, with 127 usable slots reserved by the \texttt{next != g\_ring\_tail} full-queue check). When a bus error occurs, \texttt{protocol\_error\_isr()} clears all hardware error flags via ST HAL macros~\cite{um1785} and immediately re-arms the receive interrupt, enabling seamless recovery from cable glitches.

\subsection{Bounded Frame Assembly and Incomplete Frame Timeout}

An authoritative embedded server must defend against malformed inputs. If a client transmits an unbounded stream of characters without a newline, an unconstrained buffer will overrun RAM, inducing undefined behavior or hard faults. Conversely, if an oversized frame is discarded prematurely mid-stream, trailing bytes bleed into subsequent valid commands, corrupting state.

\begin{lstlisting}[language=C, caption={Frame assembly with 64-byte overflow protection and timeout (\texttt{protocol.c}).}, label=lst:poll]
void protocol_poll(void) {
    uint32_t now = HAL_GetTick();
    /* Clear incomplete frames after 500 ms timeout */
    if (g_frame_len > 0 && (now - g_frame_last_rx >= PROTOCOL_FRAME_TIMEOUT_MS)) {
        g_frame_len = 0;
        g_frame_overflow = false;
        protocol_send("NACK:BADCMD\n");
    }
    while (g_ring_tail != g_ring_head) {
        uint8_t c = g_ring_buf[g_ring_tail];
        g_ring_tail = (g_ring_tail + 1) % PROTOCOL_RING_BUFFER_SIZE;
        if (c == '\r') continue;
        if (c == '\n') {
            if (g_frame_overflow) {
                g_frame_overflow = false;
                g_frame_len = 0;
                protocol_send("NACK:BADCMD\n");
            } else if (g_frame_len > 0) {
                g_frame_buf[g_frame_len] = '\0';
                protocol_dispatch_command(g_frame_buf);
                g_frame_len = 0;
            }
            continue;
        }
        if (!g_frame_overflow) {
            if (g_frame_len < PROTOCOL_MAX_FRAME_LEN) {
                g_frame_buf[g_frame_len++] = (char)c;
                g_frame_last_rx = HAL_GetTick();
            } else {
                g_frame_overflow = true;
            }
        }
    }
}
\end{lstlisting}

Listing~\ref{lst:poll} shows the frame assembly loop in \texttt{protocol\_poll()}. It consumes bytes from the ring buffer, silently discards carriage returns (\texttt{\textbackslash r}), and stores characters in \texttt{g\_frame\_buf} (sized at 65 bytes to accommodate up to 64 payload characters plus a null terminator). If a line exceeds 64 characters without a newline, \texttt{g\_frame\_overflow} latches to true, and subsequent bytes are discarded until \texttt{\textbackslash n} arrives, at which point the server returns \texttt{NACK:BADCMD\textbackslash n}. This prevents partial remnants (e.g. \texttt{E:X:0}) from triggering cascading syntax errors. Additionally, if an incomplete frame stalls in the buffer for longer than \texttt{PROTOCOL\_FRAME\_TIMEOUT\_MS} (500\,ms) without receiving a delimiter, \texttt{protocol\_poll()} purges the buffer and returns \texttt{NACK:BADCMD\textbackslash n}, satisfying the compulsory requirement for automatic timeout clearance.

\subsection{Non-Blocking Software Debounce Isolates Game State from Switch Noise}

Mechanical push buttons bounce for 10 to 30\,ms upon contact closure. Triggering on raw GPIO transitions or hardware external interrupts causes repeated reset events, while inserting a blocking delay (\texttt{HAL\_Delay(50)}) freezes the CPU, causing the UART interrupt buffer to overflow and drop client commands.

Listing~\ref{lst:debounce} shows the non-blocking debouncer in \texttt{hardware.c}. It samples the input pin during each main loop iteration against \texttt{HAL\_GetTick()}. Any transition restarts the debounce counter. Only after the pin remains stable for a continuous 50\,ms is the new level latched into \texttt{g\_btn\_stable}. On an active-low falling edge, the game is safely re-initialised to \texttt{IDLE} and the status LEDs are extinguished, without stalling protocol processing.

\begin{lstlisting}[language=C, caption={Non-blocking 50\,ms button debouncer (\texttt{hardware.c}).}, label=lst:debounce]
void hardware_update(void) {
    uint32_t now = HAL_GetTick();
    GPIO_PinState raw = HAL_GPIO_ReadPin(GPIOA, UCT_SW0_Pin);
    if (raw != g_btn_last_raw) {
        g_btn_last_time = now;
        g_btn_last_raw = raw;
    }
    if ((now - g_btn_last_time) >= BUTTON_DEBOUNCE_MS) {
        if (raw != g_btn_stable) {
            g_btn_stable = raw;
            if (g_btn_stable == GPIO_PIN_RESET) {
                game_init();
                HAL_GPIO_WritePin(GPIOB, UCT_LED_RED_Pin | 
                                         UCT_LED_GREEN_Pin, 
                                  GPIO_PIN_RESET);
            }
        }
    }
}
\end{lstlisting}

\subsection{Client Request-Response Timeout Prevents GUI Thread Freezes}

In graphical applications, blocking calls on the main event thread cause the operating system to flag the window as unresponsive. If the serial cable is disconnected mid-game or the STM32 loses power, standard calls (such as Python's default \texttt{readline()}) hang indefinitely. Relying on unconstrained \texttt{readline()} also caused Windows driver buffering issues where partial lines were cached, desynchronizing subsequent reads.

\begin{lstlisting}[language=Python, caption={Bounded request-response reader with timeout (\texttt{serial\_client.py}).}, label=lst:serialclient]
def send_command(command):
    global connection
    if connection is None:
        return None
    try:
        msg = (command.strip() + "\n").encode("ascii")
        connection.write(msg)
        response = bytearray()
        while len(response) < MAX_RESPONSE_LENGTH:
            byte = connection.read(1)
            if not byte: # Timeout or cable disconnect
                disconnect()
                return None
            if byte == b"\n":
                break
            if byte != b"\r":
                response.extend(byte)
        else: # Exceeded 64 bytes without newline
            disconnect()
            return None
        return response.decode("ascii")
    except (OSError, serial.SerialException):
        disconnect()
        return None
\end{lstlisting}

Listing~\ref{lst:serialclient} illustrates \texttt{send\_command()} in \texttt{serial\_client.py}. The client configures PySerial with a per-read timeout of $1.0\,\text{s}$ (\texttt{timeout=1.0}), distinct from the microcontroller's 500\,ms incomplete-frame timeout. It consumes responses byte-by-byte up to \texttt{MAX\_RESPONSE\_LENGTH} (64 bytes). If the link stalls or disconnects, \texttt{connection.read(1)} times out, returns \texttt{None}, and cleanly releases system resources, allowing the GUI to display a reconnection dialog without hanging.
